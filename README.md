# Event Budget API

A REST API for storing events (weddings, birthdays, corporate parties, etc.)
along with their budgets: an organizer, optional collaborators, and a
line-item budget breakdown by category (venue, catering, etc.) with budgeted
vs. actual spend.

**Stack:** Python 3.12, FastAPI, SQLAlchemy 2.0, PostgreSQL, Alembic.
**Deploy target:** AWS API Gateway (HTTP API) + Lambda (container image) +
RDS Postgres.

## Data model

**Event**
| Field | Type | Notes |
|---|---|---|
| `id` | UUID | server-generated |
| `name` | string | required |
| `event_type` | enum | wedding / birthday / anniversary / corporate / baby_shower / graduation / other |
| `event_date` | date | optional |
| `location` | string | optional |
| `host_name` | string | optional |
| `organizer_email` | email | **required** — main point of contact |
| `collaborator_emails` | list of emails | optional — others with visibility into the event |
| `guest_count` | int | optional |
| `total_budget` | decimal | optional overall budget |
| `notes` | text | optional |
| `budget_items` | list of BudgetItem | see below |

**BudgetItem** (belongs to one Event)
| Field | Type | Notes |
|---|---|---|
| `category` | string | e.g. "Venue", "Catering" |
| `description` | string | optional |
| `budgeted_amount` | decimal | required |
| `actual_amount` | decimal | optional — what was actually spent |
| `vendor_name` | string | optional |
| `paid` | bool | default false |

## Endpoints

| Method | Path | Description |
|---|---|---|
| `POST` | `/events` | Create an event (with an optional list of budget items) |
| `GET` | `/events` | List events; optional `?name=` filter (case-insensitive partial match) |
| `GET` | `/events/{event_id}` | Fetch one event by ID, including its budget items |
| `PUT` | `/events/{event_id}` | Full update — replaces the event's fields **and** its entire budget_items list with what you send |

Interactive docs (Swagger UI) are auto-generated by FastAPI at `/docs` once
the app is running.

### Authentication

Every `/events*` route requires an `X-API-Key` header matching the `API_KEY`
environment variable; requests without it (or with the wrong value) get a
401. `/health` is unauthenticated. In AWS, `API_KEY` is set as a Lambda
environment variable with the value pulled from Secrets Manager, same as
`DB_PASSWORD` — see [docs/AWS_CONSOLE_SETUP.md](docs/AWS_CONSOLE_SETUP.md).

Note on `PUT`: this is a full replace, standard REST semantics. If you PUT
an event with 1 budget item and it previously had 3, the other 2 are
deleted. There's no `PATCH` (partial update) or `DELETE` endpoint in this
version — see "Possible next steps" below if you want to add either.

## Local development

Requires Python 3.9+ and Docker. Do the one-time setup, then the three
pieces below (database, API, tests) can each be run independently once it's
done.

### One-time setup

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt

cp .env.example .env   # docker-compose.yml reads its Postgres credentials from this file
```

### 1. Run the database

Postgres runs in Docker; nothing to install locally.

```bash
docker compose up -d        # starts Postgres on localhost:5432, in the background
docker compose ps           # check it's up and healthy
alembic upgrade head        # create/update the events & budget_items tables
```

To stop it: `docker compose down` (add `-v` to also delete the data volume
and start clean next time). Logs: `docker compose logs -f db`.

### 2. Run the API

With the database running and migrations applied:

```bash
source .venv/bin/activate   # if not already active
uvicorn app.main:app --reload
```

The API is now at `http://127.0.0.1:8000`, with interactive Swagger docs at
`http://127.0.0.1:8000/docs` (try requests directly from the browser there).
`--reload` restarts the server automatically as you edit `app/*.py`.

### 3. Run the tests

Independent of whether the API server (step 2) is running — the tests talk
to the database directly.

```bash
source .venv/bin/activate   # if not already active
docker compose up -d        # tests need Postgres running too
pytest tests/ -v
```

This creates its own `events_test` database on the same Postgres container
and rolls back every test, so it never touches the dev data you created
while poking at the API in step 2.

### Example requests

```bash
curl -X POST http://127.0.0.1:8000/events \
  -H "Content-Type: application/json" \
  -H "X-API-Key: <your-api-key-from-.env>" \
  -d '{
    "name": "Alex & Sam Wedding",
    "event_type": "wedding",
    "event_date": "2026-09-12",
    "location": "Napa Valley, CA",
    "organizer_email": "alex@example.com",
    "collaborator_emails": ["sam@example.com"],
    "guest_count": 120,
    "total_budget": 45000,
    "budget_items": [
      {"category": "Venue", "budgeted_amount": 15000, "vendor_name": "Napa Vineyards"}
    ]
  }'

curl "http://127.0.0.1:8000/events?name=wedding" -H "X-API-Key: <your-api-key-from-.env>"
curl http://127.0.0.1:8000/events/<event_id> -H "X-API-Key: <your-api-key-from-.env>"
curl -X PUT http://127.0.0.1:8000/events/<event_id> -H "Content-Type: application/json" -H "X-API-Key: <your-api-key-from-.env>" -d '{...}'
```

### Changing the schema

This project uses Alembic migrations rather than `create_all()`, so schema
changes are tracked and reproducible:

```bash
# after editing app/models.py
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```
